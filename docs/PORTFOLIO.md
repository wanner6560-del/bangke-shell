# 蚌壳 · 项目经历与面试讲述

## 一句话介绍

蚌壳是一款通过人机协作构建的移动优先视觉日记 PWA，将截图、文字和情绪片段整合成私人档案，并支持拼贴回看和视觉卡片分享。

## 角色说明

这是个人产品原型。发起者负责生活场景、审美偏好、体验目标、功能优先级与验收反馈；AI 编程助手协助产品拆解、前端实现、设计迭代、验证和工程文档。适合将个人角色表述为“独立产品策划、设计与 AI 协作开发”，不应宣称所有代码都手工独立编写。

## 可直接放入简历的版本

**蚌壳 SHELL｜独立产品设计与 AI 协作开发｜个人原型项目**

- 针对截图、日记与灵感分散存储、缺少情绪化回看体验的问题，定义“私人视觉档案”产品方向，完成需求收敛、视觉系统与交互方案。
- 通过自然语言提出需求与验收标准，与 AI 编程助手协作，使用 React 19、Vite 8 构建移动端优先的 PWA，实现图文记录、本地持久化、拼贴 / 网格 / 时间线浏览、Canvas 视觉卡片导出与每日句子。
- 将完整宠物养成与真实 AI 接入分阶段处理，先验证记录—回看—分享链路；为公开演示准备虚构文案与原创 SVG，配置 GitHub Pages 工作流并编写产品、架构和交接文档。

**阶段与证据：** 可交互原型。可展示源代码、产品案例、部署构建与操作过程；AI 旁注和推荐仍为预设示例，无真实调用。尚无规模化用户验证。

## 90 秒讲述

“我做这个项目，是因为发现自己保存了很多画面和片段文字，但它们分散在相册与备忘录中，很难再找回当时的感受。我希望做一个有审美、容易打开、也允许零碎表达的私人空间。

我先把需求从‘自己的小豆瓣’收敛为‘私人视觉档案’，用图文记录、自由拼贴与有序档案来解决保存和回看的问题。分享上选择视觉卡片，只导出当前摘录，减少公开整篇日记的负担。

开发采用与 AI 编程助手协作的方式。我负责提出场景、审美和优先级，通过具体页面与交互判断结果，AI 帮助实现 React 界面和工程配置。一个关键取舍是先不做完整独角兽养成，也先不接真实 AI，而是把最小的记录、回看和分享路径做完整。

当前交付是一套可操作的 PWA 原型与独立项目案例。下一步我会优先改进图片存储和备份，再找少量目标用户验证他们是否愿意回来，而不是立即继续堆功能。”

## 面试中可以深入的决策

| 问题 | 可讨论内容 | 可展示证据 |
| --- | --- | --- |
| 为什么用网页而非原生 App？ | 链接分发、低安装门槛、同一代码库覆盖多端 | Manifest、响应式布局、Pages 工作流 |
| 如何平衡自由与秩序？ | 同一记录模型支持不同布局，避免强制分类 | 漂流模式切换、档案视图 |
| Vibe coding 的个人贡献是什么？ | 场景定义、优先级、审美反馈、验收与边界判断 | 产品方案、当前原型、范围取舍 |
| 为什么不直接接 AI？ | 先验证核心体验，避免费用与未经验证的生成能力 | 预设内容标签、未来 AI 架构 |
| 本地存储有什么不足？ | 配额、同步写入、图片体积、清理丢失、无备份 | localStorage 代码、IndexedDB 计划 |
| 如何保护分享边界？ | 卡片不导出完整正文和分析；用户仍需检查摘录 | Canvas 导出字段 |

## 演示脚本（约 3 分钟）

1. 打开 `/showcase/`，介绍产品命题和三个使用摩擦。
2. 切换功能标签，点击“漂流拼贴”手机预览中的布局按钮。
3. 进入 `/`，跳过开屏，保存一条不含私人信息的图文记录。
4. 在漂流与档案找到它，打开详情，生成并下载视觉卡片。
5. 回到展示页说明当前 AI 为示例，以及下一步为何优先做存储和备份。

## 请保留的事实边界

没有真实用户量、增长、留存或商业收入数据；没有完整电影识别或实时生成；没有公开研究证实的疗愈效果。日期和投入时长应使用本人能确认的记录，不根据对话时间推算工时。

讲述重点是：如何定义问题、如何做取舍、如何验收 AI 协作的结果，以及能解释当前技术选择的局限。
